# sad_spirit/el2sql: Expression Language to SQL translator

Suppose we need to get all database records satisfying a condition written in [Symfony's ExpressionLanguage].
We can fetch everything from the DB and then filter the result through `$expressionLanguage->evaluate()`,
but a much nicer approach is to translate the expression to SQL and make the database do the job.

This package allows exactly this: given an ExpressionLanguage condition it generates a `WHERE` clause part
in Postgres dialect of SQL.

Let's start with a simple example: an expression using a single variable. Having a table with the following schema
```SQL
create table example.documents (
    doc_id integer not null generated by default as identity,
    doc_title text not null,
    doc_text text not null,
    doc_state text not null,

    constraint documents_pkey primary key (doc_id),
    constraint documents_allowed_state check ( doc_state in ('draft', 'rejected', 'approval', 'published') )
);
```
we can map its rows to DTOs
```PHP
use sad_spirit\el2sql\attributes\{
    PropertyToColumnTransformation,
    Table
};

#[PropertyToColumnTransformation(addPrefix: 'doc_')]
#[Table('example', 'documents')]
final readonly class Document
{
    public function __construct(
        public int $id,
        public string $name,
        public string $text,
        public string $state,
    ) {
    }
}
```
Note the attributes applied to the class, those describe how property accesses in an expression are translated to SQL.

A DTO like this can be used as a variable in Expression Language expression
```PHP
use Symfony\Component\ExpressionLanguage\ExpressionLanguage;

$result = (new ExpressionLanguage())->evaluate(
    "document.state in ['draft', 'published']",
    ['document' => new Document(/* ... */)]
);
```
which checks whether this particular document has a correct state. Now let's use the same expression to fetch *all*
documents with the correct states:
```PHP
use sad_spirit\el2sql\{
    TranslatableExpressionLanguage,
    translators\DefaultPropertyTranslatorFactory
};
use sad_spirit\pg_builder\Statement;
use sad_spirit\pg_gateway\{
    TableGateway,
    TableLocator,
    builders\FluentBuilder,
    fragments\CustomFragment,
    walkers\ReplaceTableAliasWalker
};
use sad_spirit\pg_wrapper\Connection;

$connection = new Connection('...');
$locator    = new TableLocator($connection);
$language   = new TranslatableExpressionLanguage(null, [], [new DefaultPropertyTranslatorFactory($locator)]);
// This builds a mapping from class properties to database columns, used later in translation 
$language->getVariableMapper()
    ->map('document', Document::class);

$query = $locator->select('example.documents', fn (FluentBuilder $builder) => $builder
    ->add($language->translate("document.state in ['draft', 'published']", ['document'])
            ->getCondition())
    // The translated Condition will use variable name (i.e. 'document') as a table alias,
    // need to change this to default 'self' used by pg_gateway
    ->add(new class ('alias-self', \PHP_INT_MIN) extends CustomFragment {
        public function applyTo(Statement $statement): void
        {
            $statement->dispatch(new ReplaceTableAliasWalker('document', TableGateway::ALIAS_SELF));
        }
    }));

echo $query->createSelectStatement()->getSql();
```
The generated query printed on the last line is
```SQL
select self.*
from example.documents as self
where self.doc_state = any(array['draft', 'published'])
```

## How does this work?

ExpressionLanguage has a `parse()` method that builds an AST for the expression.
This is then transformed into AST for Postgres dialect of SQL,
which is represented using classes from [pg_builder package].

Transforming ASTs is actually an easier part, the harder part is mapping of object properties to database columns and
translating custom functions.

## What parts of ExpressionLanguage are *not* supported

### Object methods

These do not have a suitable counterpart in Postgres. You'll have to use (virtual) public properties
instead of getters or plain functions if there is a need to pass additional arguments.

### Null-safe Operator

It does not make sense in the context of this package: if a variable is missing
then a lookup query should be built for that table.

## Example

Let's consider a more complex business rule that may appear in some document approval scenario:
```
document.author in employee.subordinates
```

Two types of queries are possible based on that
- Fetch all documents that are authored by subordinates of the given employee;
- Fetch all managers for the author of the given document.

Additionally, while `document.author` will probably map to a column of the `documents` table,
`employee.subordinates` will probably not be that simple: subordination is often represented using
a department tree with employees linked to the branches of that.
